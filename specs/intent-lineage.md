# Task: Add intent artifact and lineage contract

## Context

RepoMethod currently begins durable delivery at the technical feature spec. GitHub
issue #14 adds an optional upstream intent artifact so a later agent can recover
why the feature exists without requiring chat history. Stage 1 establishes only
the source artifact and deterministic spec reference; workflow-state binding and
end-to-end status/handoff surfaces are reserved for later review stages.

## Objective

Provide one optional, deterministic, fail-closed intent-to-spec lineage contract
without changing Quick MVP or legacy Classic/Graph specs that have not opted in.

## Definition of Ready

- Intent content remains upstream product/system purpose, not an implementation plan.
- The repository convention is `intents/<feature>.md`.
- The spec binding has one deterministic path/content identity representation.
- One script owns generation and validation of that representation.
- Stage 2 workflow-state binding and Stage 3 downstream surfaces remain excluded.

## Source Intent

```json
{"path":"intents/intent-lineage.md","schema_version":1,"sha256":"0d431764f80b46340a5d681be91720a2d41196f539ac92741950e30845519634"}
```

## Architecture and Authority Boundaries

`intent-lineage.sh` is the sole authority for intent binding generation and
validation. The intent file is durable repository content. A feature spec stores
only the canonical binding generated by that script. Other gates may invoke the
authority but must not independently calculate or parse intent identity.

## Dependencies and Interfaces

- Intent artifacts use only Markdown plus repository-local SHA-256 tooling.
- Feature specs optionally declare `## Source Intent` with the canonical JSON binding.
- The full spec gate invokes the canonical checker; Quick MVP never reaches it.

## Plan Obligations

- `intent-template` [shape] The canonical intent template contains only problem, desired outcome, affected users/systems, constraints, non-goals, open questions, and provenance/source.
- `source-intent-binding` [shape] An opted-in feature spec stores one canonical JSON binding with schema version, exact `intents/<feature>.md` path, and a lowercase SHA-256 content identity.
- `canonical-lineage-authority` [process] One script owns creation and validation of intent lineage identity; downstream callers do not implement a second hash or parser.
- `intent-validation` [behaviour] Missing, malformed, substituted, symlinked, or content-stale intent references fail closed after opt-in.
- `legacy-spec-backcompat` [behaviour] A spec with no live Source Intent binding remains not applicable and retains prior behavior.
- `quick-unaffected` [prohibition] Quick MVP gains no intent artifact, spec, state, or lineage requirement.
- `stage-boundary` [prohibition] Stage 1 does not bind intent into workflow state or add status/handoff/closeout lineage surfaces.

## Out of Scope

- Workflow-state intent binding or resume logic (Stage 2).
- Status, handoff, delivery, or closeout lineage surfaces (Stage 3).
- Issue #5 plan provenance changes and issue #6 plan-conformance changes.
- External trackers, model calls, databases, queues, or hosted state.

## Acceptance Criteria

1. The canonical intent template contains only the deliberately small upstream fields required by issue #14.
2. `intent-lineage.sh pin` emits a deterministic binding for `intents/<feature>.md` using exact file-byte SHA-256 identity.
3. `intent-lineage.sh check` accepts a current canonical binding and rejects malformed, missing, substituted, symlinked, or stale references.
4. Specs without a live intent binding remain backward compatible.
5. The full spec gate invokes the canonical lineage checker while Quick MVP remains unchanged.
